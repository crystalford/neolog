# Neolog — System Vision

> Read this before writing any code. It overrides defaults.

---

## What Neolog Is

A **life ingestion engine**. Any input a user produces — video rant, voice memo, pasted chat log, text dump, LLM conversation — becomes raw material for a growing intelligence layer that synthesizes across sessions and eventually generates finished artifacts.

**The stack: Log → Blog → Vlog.** Three output modes, one data layer.

- **Log**: every session captured and structured
- **Blog**: synthesized writing generated from accumulated sessions
- **Vlog**: AI-edited video assembled from raw footage using entity graph as narrative context

**The loop**: ingest privately → synthesize → publish automatically.

---

## What Neolog Is Not

- Not a productivity dashboard
- Not a note-taking app (retrieval is not the goal — synthesis is)
- Not a social platform
- Not a writing editor (the user doesn't write; the system generates)

---

## The Technical Reality

This is a personal RAG (retrieval-augmented generation) system built on life data. The "intelligence" is Claude API called with the user's entity graph as context before each session. Claude is stateless — briefed from the database every call, not learning.

**Version 1** (current): structured capture → entity graph → RAG-based Claude sessions
**Version 2** (future): fine-tune a small model on 12-18 months of accumulated sessions, entity corrections, and artifact feedback. That model doesn't need briefing — it knows the user the way a base model knows English.

Version 1 is simultaneously the product and the training data pipeline for Version 2. **Every entity correction is a label. Every artifact edit is a signal. Session quality matters.**

---

## Multi-Tenant Architecture Principle

**The system is built for a type of mind, not a specific person. The founder is user zero — the first person to run the full system against their own life.**

Nothing about any specific user's projects, habits, creative works, or patterns should appear in code, prompts, or architecture. Those are **data**. The system is the **container**.

Concretely:
- Never hardcode project names, user names, or personal identifiers in source code
- Never write `if user === 'someone'` conditions
- All entity types, synthesis logic, and artifact generation are universal
- The public profile, living resume, and output surfaces are per-user by design

## Data Model Principles

### Polymorphic entity_mentions (non-negotiable)

Every entity mention links to exactly one source, identified by `source_type`:

| source_type | foreign key | used when |
|---|---|---|
| `video` | `video_upload_id` | processed video/audio upload |
| `chat` | `log_entry_id` | chat session archived |
| `capture` | `log_entry_id` | text/voice capture |
| `import` | `log_entry_id` | imported external content |

All inputs land as `log_entries` (except video, which uses `video_uploads`). Never create a separate extraction path that bypasses the entity graph.

### Unified timeline

All session types produce a `log_entry`. Video uploads produce a `video_upload` (which references the `log_entry` when one is created). Every session is in the timeline.

### Entities accumulate, never reset

An entity's `mention_count`, `first_mentioned_at`, `last_mentioned_at`, and `summary` update with every new mention. The summary is regenerated by the synthesis job as more context accumulates — it is not a static first-impression snapshot.

### Framing is data

The *framing* of an entity (how the user is currently relating to a project, how they describe an idea) is captured as `context` on each `entity_mention`. Contradiction detection in Phase 4 diffs these framings over time. This is why context must be rich and specific, not generic.

## Build Phases (summary)

| Phase | What the system knows |
|---|---|
| 0 | Sessions happened |
| 0.5 | Extracted entities are real (prompt validated) |
| 1 | Same concept appeared across multiple input types |
| 2 | User can see their own history on any entity |
| 3 | Which entities are connected and how strongly |
| 4 | How thinking about something has changed over time |
| 5 | Where the user is right now, always |
| 6 | Patterns the user didn't consciously notice |
| 7 | System can generate finished material from accumulated input |
| 8 | System can publish — the vault becomes a publishing engine |

---

## The Extraction Prompt Is the Intelligence

The Claude analysis prompt in `src/lib/video-analysis.ts` is not a detail. It is the intelligence layer. Every phase downstream is only as good as what it extracts.

The prompt must version itself: every analysis response includes `"analysis_version"` so we can track which prompt generated which data. When the prompt improves, historical data doesn't corrupt — it's tagged with its version.

Do not modify the extraction prompt casually. Test against real sessions first. The quality of the entity graph is entirely dependent on it.

---

## Verification Principle

Every feature must be verifiable by querying raw DB rows — not by looking at UI changes. If you can't confirm it worked via `SELECT`, it's not done.

---

## The Long Arc

The logical endpoint of Log → Blog → Vlog is interactive narrative. The entity graph is a spatial structure, currently rendered as a list. Eventually: navigable space. A user's creative history, projects, and thinking — not as text or video but as something you move through. That's version 4. The same data all the way down.
